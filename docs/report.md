# Отчет: регистрация событий на видеозаписи

## Постановка задачи

Цель проекта - построить систему, которая анализирует видеозапись одного человека и регистрирует действия как временные события. Результат системы - структурированный журнал:

```json
{
  "label": "walk",
  "start_sec": 5.0,
  "end_sec": 10.0,
  "avg_confidence": 0.82,
  "max_confidence": 0.91
}
```

Задача отличается от обычной классификации видео: нужно не только определить действие, но и найти его границы во времени.

## Датасет

Финальная версия проекта обучалась на локальном наборе из 82 видео:

```text
data/dev/raw/
data/dev/annotations.csv
```

Разметка имеет формат:

```csv
video,start_sec,end_sec,label
```

Всего:

```text
82 видео
716 размеченных событий
8 классов
```

Классы: `stand`, `walk`, `run`, `jump`, `push_ups`, `squat`, `bend`, `other`.

Split выполнен по исходным видео:

```text
train: 57 видео, 489 событий
val:   12 видео, 107 событий
test:  13 видео, 120 событий
```

Такой split честнее, чем случайное разделение по клипам, потому что события из одного видео не попадают одновременно в train и test.

## Анализ референсов

`IIharlamovv/action-recognition-v1.0` полезен как ориентир по video action recognition: видеофрагменты, 3D-CNN/X3D, sliding window inference, CSV-разметка событий и JSON-экспорт. Его датасет не был использован как полноценный обучающий набор, потому что в репозитории нет всех обучающих видео.

`Realtime-Action-Recognition` технически устарел: TensorFlow 1.x, OpenPose/tf-pose-estimation, PCA, ручные признаки и MLP не подходят как база современного проекта. Но его общие идеи temporal window, smoothing, confidence threshold и стабильной метки во времени были переосмыслены в новом pipeline.

## Архитектура

Общая цепочка:

```text
validation -> split -> train -> inference -> EventRegistry -> evaluation -> visualization
```

Основные модули:

```text
validation.py      # проверка CSV и видео
dataset.py         # PyTorch Dataset для размеченных событий
models.py          # r3d_18 и checkpoint logic
events.py          # регистрация событий
pipeline.py        # inference по длинному видео
metrics.py         # event-level метрики
visualization.py   # timeline
repetitions.py     # подсчет повторений
```

## Модель

Используется `r3d_18` из `torchvision.models.video`:

```text
pretrained r3d_18 -> final layer на 8 классов
```

Вход модели:

```text
[B, C, T, H, W]
```

Конфиг финального обучения:

```text
configs/final.yaml
```

Checkpoint:

```text
models/final_checkpoint.pt
```

## Стратегия обучения

Обучение выполнено в два этапа:

1. `head_warmup`: обучается классификационная голова.
2. `last_block_finetune`: размораживается последний блок `layer4` и голова.

Это снижает риск переобучения на сравнительно небольшом пользовательском датасете.

Дополнительно используются:

- pretrained backbone;
- class weights;
- balanced sampler;
- label smoothing;
- augmentation;
- cosine learning rate schedule;
- сохранение лучшего checkpoint.

## Регистрация событий

`EventRegistry` превращает поток оконных предсказаний в события:

- применяет `confidence_threshold`;
- сглаживает метки через `smoothing_window`;
- отсекает слишком короткий шум;
- склеивает одинаковые события через короткую паузу;
- закрывает последнее событие в конце видео.

## Подсчет повторений

Для периодических действий добавлен отдельный post-processing:

- `push_ups`;
- `squat`;
- `bend`;
- `jump`.

Счетчик не меняет checkpoint модели. 3D-CNN отвечает за класс и границы события, а счетчик анализирует уже найденный интервал. В сильном режиме используется гибридный подход: MediaPipe Pose для pose-friendly классов и motion-energy fallback.

## Метрики

На validation:

```text
best_val_acc  = 0.9813
best_val_loss = 0.3415
```

На held-out test split:

```text
precision = 0.8189
recall    = 0.8667
f1        = 0.8421
mean_iou  = 0.6658
latency   = 1.5105 sec
```

`val_acc = 0.9813` is clip-level classification accuracy — how well the model classifies individual 16-frame clips. `test F1 = 0.8421` is event-level detection quality — how well the full pipeline finds events with correct temporal boundaries in a long video. These metrics measure different things and cannot be compared directly.

По классам:

```text
push_ups: F1 1.0000
squat:   F1 0.9655
run:     F1 0.8824
jump:    F1 0.8667
other:   F1 0.8571
stand:   F1 0.7778
walk:    F1 0.7692
bend:    F1 0.6923
```

Метрики показывают, что pipeline работает и модель стала заметно сильнее после расширения набора данных. При этом результат не стоит трактовать как production-grade: часть видео снята в похожих условиях, а два test-видео дали слабые event-level результаты.

## Эксперимент X3D-S

Дополнительно был проведен отдельный эксперимент с архитектурой `X3D-S` из `pytorchvideo`. Это не замена финальной модели, а честное сравнение альтернативного video backbone.

Условия эксперимента:

```text
R3D-18: image_size = 112, checkpoint около 127 MB
X3D-S:  image_size = 160, checkpoint около 12 MB
```

Это важно фиксировать: модели сравнивались на одном train/val/test split и на одной event-level оценке, но spatial context у них разный. Для `X3D-S` был использован больший размер кадра, потому что эта архитектура чувствительнее к spatial input.

Для `X3D-S` была сделана отдельная temperature calibration:

```text
models/x3d_s_temperature.json
temperature = 0.1643
```

У финальной `R3D-18` используется другой файл:

```text
models/temperature.json
temperature = 0.6008
```

Для `X3D-S` отдельно был выполнен `confidence_threshold` sweep по validation split:

```text
outputs/x3d_s/threshold_sweep_val/threshold_sweep.csv
лучший threshold по validation: 0.70
val F1 = 0.9358
val mean_iou = 0.7815
```

После этого `X3D-S` была один раз оценена на test split с выбранным на validation threshold. Это делает сравнение честнее: test не использовался для выбора порога.

Сравнение на test split:

| Модель | Precision | Recall | F1 | Mean IoU | Latency | Размер checkpoint |
|---|---:|---:|---:|---:|---:|---:|
| R3D-18 | 0.8189 | 0.8667 | 0.8421 | 0.6658 | 1.5105 sec | ~127 MB |
| X3D-S, threshold 0.55 | 0.7591 | 0.8667 | 0.8093 | 0.7355 | 1.1316 sec | ~12 MB |
| X3D-S, threshold 0.70 | 0.7704 | 0.8667 | 0.8157 | 0.7321 | 1.1573 sec | ~12 MB |

Главный результат эксперимента: tuning threshold немного улучшил `X3D-S` (`F1: 0.8093 -> 0.8157`, `FP: 33 -> 31`), но не перевел ее выше `R3D-18` по итоговому `F1`. При этом `X3D-S` стабильно дает существенно лучший `Mean IoU`: `0.6658 -> 0.7321`. Для задачи регистрации событий это важный результат, потому что качество временных границ является принципиальной частью задачи. Кроме того, `X3D-S` примерно в 10 раз компактнее по размеру checkpoint, что делает ее перспективной для edge/mobile сценариев.

Итоговая формулировка: `R3D-18` выбрана финальной моделью по event-level `F1` и меньшему числу false positives. `X3D-S` показала лучшую локализацию границ при размере модели примерно в 10 раз меньше; это сильное направление для дальнейшей работы, особенно если отдельно подобрать `confidence_threshold` и параметры post-processing под эту архитектуру.

## Анализ ошибок

Самые слабые test-видео в текущей оценке - `10.MOV` и `7.MOV`. Они сложнее среднего, потому что модель хуже переносит выученные признаки на их конкретный ракурс, темп и границы переходов между действиями. На таких роликах сильнее проявляется ограничение текущей архитектуры: модель классифицирует короткие клипы длиной `clip_len=16`, то есть примерно около 1 секунды контекста, а событие в длинном видео может иметь плавное начало и конец.

Для `10.MOV` основные ошибки связаны с `stand`, `run`, `jump`, `bend`, `other` и `walk`: часть событий либо пропускается, либо получает лишние предсказания рядом с переходами. Это похоже на проблему границ и короткого контекста: в момент перехода человек может еще не выполнять действие в полной форме, но визуально уже не находится в предыдущем классе.

Для `7.MOV` заметнее всего страдают `bend`, `run`, `stand`, `other` и `walk`. `push_ups` и часть `jump` распознаются лучше, потому что эти действия имеют более выраженный визуальный паттерн. `bend`, `walk` и `stand` хуже разделяются между собой: наклон может быть похож на подготовку к другому упражнению, ходьба может выглядеть как переход, а стойка часто возникает короткими фрагментами между активными действиями.

Эти ошибки связаны с известными ограничениями модели: короткое временное окно, похожие позы у классов `bend/walk/stand`, одночеловеческий датасет с ограниченным разнообразием ракурсов и отсутствие отдельной модели для точной локализации границ. Добавленное boundary refinement снижает часть ошибок на границах, но не заменяет необходимость расширять данные для слабых классов.

## Ограничения

Текущая версия решает single-person задачу. Multi-person tracking оставлен как future work, его можно добавить через person detector + tracker.

Слабые классы сейчас: `bend`, `walk`, `stand`. Для дальнейшего улучшения нужны дополнительные видео с разными ракурсами, людьми, фонами, освещением и порядком действий.

## Вывод

Проект не копирует GitHub-референсы напрямую. Из них взяты сильные идеи, но итоговая система собрана как самостоятельный современный pipeline: validation, video split, staged fine-tuning, event registry, evaluation, timeline, annotated video, Streamlit demo и repetition counting.
